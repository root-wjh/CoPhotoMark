## 3. 智星云环境

GPU只加速InsightFace检测；DCT、水印、攻击生成、统计仍在CPU运行。选择CPU核数和内存也影响耗时。

```bash
conda create -n cpm python=3.10 -y
conda activate cpm
cd /root/CoPhotoMark_Revision
nvidia-smi
```

下面按镜像实际运行库选择一条安装命令。nvidia-smi的CUDA栏只说明驱动能力，不能证明镜像有对应cuDNN运行库：

```bash
# CUDA 12.x + cuDNN 9.x 镜像：
python -m pip install -r requirements-gpu-cu12.txt

# CUDA 11.8 + cuDNN 8.x 镜像改用下面这条（与上一条二选一）：
# python -m pip install -r requirements-gpu-cu11.txt

# 无GPU或先CPU检查：改装requirements.txt，并在命令中使用--provider cpu
```

不要在同一环境同时装onnxruntime和onnxruntime-gpu；若之前装了CPU版，应先 `python -m pip uninstall -y onnxruntime onnxruntime-gpu`，再选一个GPU依赖文件安装。老ORT配NumPy2可能不兼容，当前依赖已限制NumPy<2、OpenCV<4.12。

```bash
python -m pip check
python -m pytest -q -p no:cacheprovider
python scripts/check_environment.py --provider cuda --output audit/cloud_environment.json
```

最后一条会加载并真正执行一次检测推理，检查实际session有CUDA；只有列出CUDA可用但库加载失败时会报错，不会悄悄把CPU计时当GPU。这里尚未替你测试云端机器，不承诺所有CUDA镜像直接兼容。

## 5. 再跑整个WIDER Group子集

此本机12--Group有582张图片文件，实际唯一源图/多人图/合格ROI以清单为准，不能直接写“582张都完成多人核验”。确认上一步运行无环境错误，再跑：

```bash
python scripts/run_pipeline.py \
  --input /root/data/WIDER_Group \
  --dataset wider_group_subset \
  --config configs/full64.json \
  --output runs/wider_group_full64_v2_k3r3 \
  --keys 3 --repeats 3 --provider cuda
```

这是子集完整实验，不等于满足所有审稿要求。划分为development20%、validation20%、test其余，按数据源及人数段分组分层，四舍五入使小组比例略变。Exact文件/像素重复同组；近重复/同事件/身份信息需要用 `--groups /root/data/groups.jsonl` 提供，例如：

```json
{"relative_path":"event001/photo_a.jpg","group_id":"capture001"}
```

不能把整个12--Group文件夹都当一个事件组。WIDER大类别不是拍摄事件。缺groups时只保证文件/像素去重，不能声称身份完全独立。

流程：inventory → split → enroll3key → attacks3repeat → validation评分 → 校准并冻结 → test → report/plot。三次相同JPEG不是三张独立原图，随机供体/位置才可能随重复变化。

若目标FAR没有可行阈值，test会停止。应检查验证数据和研究假设，不能为了跑完而在test上选阈值，或随意改目标。管线无自动resume；分步CLI可重用已完成清单，`python -m cophotomark --help`查看。

主要结果：

| 路径 | 用途 |
|---|---|
| report/by_attack.csv | 全部评估实例的三态、接受率、源图CI与时延 |
| report/by_attack_full_coverage_multiface.csv | 全覆盖多人登记子表，同时对照登记总体分母 |
| report/by_attack_clean_accepted_control.csv | 同key/模式clean已通过的配对条件对照，不可拿它替换总表 |

## 6. 同一批图片的基线/消融

下面让每个方法复用主实验的源图划分与3个key，主Δ均为18。每个方法在同validation源图独立校准。不同方法若登记失败样本不同，必须报告分母与共同登记交集，不能直接混比通过率：

```bash
for cfg in roi_qim64 no_count64 no_id64; do
  python scripts/run_pipeline.py \
    --input /root/data/WIDER_Group --dataset wider_group_subset \
    --sources runs/wider_group_full64_v2_k3r3/sources.jsonl \
    --key-files runs/wider_group_full64_v2_k3r3/keys/key_0.json \
                runs/wider_group_full64_v2_k3r3/keys/key_1.json \
                runs/wider_group_full64_v2_k3r3/keys/key_2.json \
    --config configs/${cfg}.json --output runs/${cfg}_v2_k3r3 \
    --repeats 3 --provider cuda
done
```

这些是自主弱基线及结构消融，还不能代替审稿人要求的外部关键学习方法。full128为128位增强对照，full64_step24为强度对照；full64_step18与主full64相同，仅兼容旧命令名字。

## 7. 单图证明元数据在图片里

以下Linux命令不传 `--metadata`，也不生成 `.cpm.json`：

```bash
python -m cophotomark keygen --output runs/one_v2/key.json
python -m cophotomark embed-one \
  --image /root/data/WIDER_Group/你的原始图片.jpg \
  --key runs/one_v2/key.json --config configs/full64.json \
  --output runs/one_v2/marked.png --provider cuda
python -m cophotomark verify-one \
  --image runs/one_v2/marked.png --key runs/one_v2/key.json \
  --claim runs/one_v2/marked.claim.json --config configs/full64.json \
  --mode auto --output runs/one_v2/verify.json --provider cuda
```

打开verify.json：metadata_channel=image_lsb且metadata_status=valid才证明从图内读到合法元数据。最终decision仍可能因为漏脸/ROI证据失败而拒绝，不能预设通过。盲对照改 `--mode blind` 并使用不同输出文件。没有calibration的单图命令是未校准精确匹配检查。
